This is the repository for my blog.  No, this isn't the front page itself but
the README where I can stuff some notes I need about the blog.

Posts are written in org-mode, exported to Hugo-flavored markdown by ox-hugo,
and built into static HTML by Hugo.  GitHub Pages serves the result straight
out of ~docs/~ on ~main~, at [[https://blog.logustus.com][blog.logustus.com]].

* Build

Everything lives in the Nix devshell, which direnv activates on entry to the
directory.  Run the tools directly - there is no separate install step.

- ~just build~ :: The whole pipeline: re-export stale org files, rebuild the
  resume PDF, then run Hugo.  This is what you want before committing.
- ~just hugo-md~ :: Re-export stale org files to ~content/posts/~ and stop.
  Useful when you only want to see what the markdown looks like.
- ~just serve~ :: Hugo's dev server on =http://localhost:1313/=, with live
  reload.  Note it does /not/ re-export org - run ~just hugo-md~ alongside it.
- ~just resume-pdf~ :: Rebuild =static/resume.pdf= from =org/resume.org=.
- ~just resume-stamp~ :: Snapshot the current resume PDF under a dated name,
  so there's a stable artifact to attach to applications.

* Content flow

#+begin_example
  org/<slug>.org  --(emacs + ox-hugo, via scripts/build-md.el)-->
  content/posts/<slug>.md  --(hugo)-->
  docs/<slug>/index.html
#+end_example

Both intermediate and final outputs are committed.  ~docs/~ is the published
site, so a build that isn't committed is a change that isn't live.

=scripts/build-md.el= drives the export.  It is incremental: an org file is
only re-exported when it (or anything it ~#+include~'s) is newer than its
markdown.  It also reports orphaned markdown - files under ~content/posts/~
with no matching ~.org~ source.  Those are legacy Jekyll-era posts that were
converted directly to markdown; edit them in place, since there is no org
source to regenerate them from.

* Writing a post

A post needs these keywords for ox-hugo to pick it up:

#+begin_src org :results none
  ,#+title:   Some Post Title
  ,#+date:    <2026-08-07 Fri>
  ,#+hugo_base_dir: ..
  ,#+hugo_section: posts
  ,#+hugo_categories: some-category
#+end_src

~#+hugo_base_dir~ is the load-bearing one.  A file without it is treated as a
draft-in-progress and skipped rather than failing the build, which is how
unfinished drafts can sit in ~org/~ without breaking anything.

Add ~#+hugo_aliases: /<slug>.html~ on anything that existed under Jekyll, so
the legacy URL keeps resolving.

Permalinks come from the filename (~permalinks.posts: /:filename/~), so
=org/foo.org= publishes at =/foo/=.

* Assets

There are three places images live, and which one you want depends on where
the image came from:

- =org/assets/= :: Hand-authored images that belong to a post.  Reference them
  as ~[[file:./assets/foo.png]]~; ox-hugo copies them to =static/ox-hugo/= and
  emits =/ox-hugo/foo.png=.  This is the default for anything new.
- =org/= :: Artifacts generated by babel blocks - plantuml SVGs, gnuplot PNGs.
  These land next to the org source because that is where babel writes them.
  Reference as ~[[file:foo.svg]]~.
- =static/assets/= :: Jekyll-era assets, served at =/assets/foo.png=.  Nothing
  new should go here, but plenty of old posts still point at it.

* Troubleshooting

** Diagrams turn into code blocks quoting their own source

=scripts/build-md.el= must ~(require 'ob-plantuml)~.  Batch Emacs loads no user
init, so without it ~org-babel-default-header-args:plantuml~ is unbound, the
blocks fall back to ~:exports code~, and every rendered diagram silently
becomes a fenced code block containing its own source.  The same file also
pins ~org-plantuml-exec-mode~ to ~'plantuml~, because the devshell provides a
~plantuml~ wrapper on ~PATH~ rather than a jar for ~org-plantuml-jar-path~.

** An image or link 404s at =/blog/something=

Jekyll served this site under a ~/blog~ baseurl.  Hugo serves from the root,
so any surviving ~/blog/...~ path is broken.  Drop the prefix.  This bites
hardest inside ~#+begin_export html~ blocks and inline JavaScript, where
nothing rewrites the path for you.

** Raw HTML or ~<script>~ vanishes from the output

It shouldn't - ~markup.goldmark.renderer.unsafe~ is ~true~ precisely so posts
can carry inline canvas demos.  If markup really is being dropped, check that
it is inside ~#+begin_export html~ and not an indented block org has decided
is example text.

** A relative link resolves under the post's URL instead of the site root

~canonifyURLs~ is on, which resolves ~./foo.png~ against the site root rather
than the page.  ~build-md.el~ additionally rewrites ~./~ to ~/~ in the exported
markdown, so the on-disk markdown stays self-consistent.
